API Documentation

Complete reference for the Open Relay Portal REST API and WebSocket interfaces.

Introduction

Open Relay Portal provides a unified API for managing remote access to your infrastructure. All API endpoints return JSON responses and require authentication unless otherwise noted.

Base URL: All API endpoints are relative to your Open Relay Portal installation (e.g., https://portal.example.com)

Response Format

All successful responses return JSON. Error responses include an error field:

{
  "error": "Unauthorized",
  "status": 401
}

Authentication

Open Relay Portal supports the following authentication methods:

  • JWT Tokens - Session-based authentication via cookies (used by the web UI)
  • API Keys - Long-lived keys for programmatic access (prefixed portal_)
  • RTMP Tokens - Temporary, single-use publish tokens for plain RTMP streaming (prefixed rtmp_). Generated via API or the My Streams UI. Expire after 15 minutes with a 30-second grace period for reconnects.

Using API Keys

Include your API key in the Authorization header:

Authorization: Bearer YOUR_API_KEY

Or pass it as a query parameter (not recommended for sensitive operations):

GET /api/services?token=YOUR_API_KEY
POST /api/token Create session token (login)

Authenticate with username and password to receive a JWT token.

Request Body

ParameterTypeDescription
username string Your username required
password string Your password required
totp_code string Authenticator code or one-time backup code. required if the account has 2FA enabled

Two-factor accounts

For an account with 2FA enabled, a correct password alone does not issue a token. Without totp_code the endpoint returns 401 with "totp_required": true (only after the password has been verified); repeat the request with the code added. A wrong code returns 401. After 5 wrong codes within 5 minutes from one address, further attempts for that account from that address return 429 with a Retry-After header for 5 minutes; a higher per-account limit across all addresses applies as well (20 wrong codes in 15 minutes refuse further codes, from any address, until the oldest of them is 15 minutes old; Retry-After states the exact wait; when that happens an entry is added to the account's activity feed). Correct codes are also refused during a cooldown. A backup code works once. Scripts that cannot supply a code should use an API key instead.

Example

curl -X POST https://portal.example.com/api/token \
  -H "Content-Type: application/json" \
  -d '{"username": "user", "password": "pass", "totp_code": "123456"}'

Response

{
  "token": "eyJhbGciOiJIUzI1NiIs...",
  "expires_at": "2024-01-15T12:00:00Z",
  "user": {
    "id": 1,
    "username": "user",
    "is_admin": false
  }
}

API Keys

API keys provide long-lived authentication for scripts and integrations. Keys can be scoped to limit access. Send a key as Authorization: Api-Key portal_... or X-API-Key: portal_...; Bearer accepts JWTs only. Keys are stored as an Argon2id hash plus a 10-character prefix, so a lost key cannot be recovered. Each successful use updates last_used_at and last_used_ip (at most once a minute per key). A key can be bound to networks with allowed_cidrs; used from any other address it answers the same 401 as a wrong key.

Before binding keys: the portal judges the address it sees through its trusted-proxy setting (TRUSTED_PROXIES). If that is wrong, every request looks like one address and a bound key fails for everybody. Check that GET /api/admin/proxy-trust reports suspect: false (no Proxy Trust note in Admin > Overview) first, then bind one key and test it.

Checking a key that has not been used since the server started is rate limited: when too many such checks are pending for one key, the request is answered with 503 and a Retry-After header instead of 401. Retry after the given delay; the key itself is not affected.

POST /api/api-keys Create new API key (a browser session or bearer token; a request authenticated with an API key gets 403)

Request Body

ParameterTypeDescription
name string Descriptive name for the key required
scopes string Comma-separated scopes or a list (default "*" when the field is left out or null; an empty list or empty text is a 400). An unknown scope is a 400; see GET /api/api-keys/scopes. A scope is stored exactly as written, case included. Admin only; non-admin keys always get services:read,access:*
expires_days integer or "never" Days until expiration, 1 to 3650. Omitted: 90 days. "never" (or 0) for no expiry; a "*" key with no expiry gets an expiry_warning in the response. Anything unreadable is a 400.
allowed_cidrs list or string Up to 10 IPv4 or IPv6 addresses or networks the key may be used from. A /0 is refused; "any" (alone) or omitted means anywhere.
Important: The full API key is only shown once upon creation. Store it securely.

GET /api/api-keys List your API keys

Returns all API keys for the authenticated user. Keys are shown with prefix only (not full key), with their bound networks, the address each was created from and last used from (created_ip, last_used_ip). For an administrator each key also has stale: not used for 90 days.

GET /api/api-keys/scopes Scopes a key can carry

The scope registry (every scope the portal checks, with a description), plus the scopes services require (administrators only), can_choose, the limited_scopes a non-admin key always gets, and default_expiry_days. A scope an administrator made up for a service (up to 128 characters, no control characters or commas) is accepted as the service lists it, but only an administrator can name one; for anybody else it is as unknown as a made-up one. An allowed_cidrs entry with an IPv6 zone id (fe80::1%eth0) is a 400. Two live keys can share the 10-character prefix; every live key with the prefix is checked (at most 4). A refusal for the address is the security event api_key_ip_denied, aggregated per source, minute and key.

POST /api/api-keys/{id}/revoke Revoke an API key

Revokes the API key. The key will no longer work for authentication but remains in your key list. WebSockets, voice calls and in-flight proxied downloads opened with the key end at once.

DELETE /api/api-keys/{id} Delete an API key

Permanently delete an API key from your account.

Returns all active JWT tokens for the authenticated user.

Users can revoke only their own tokens. Admins can revoke tokens of users they are allowed to manage (the same hierarchy as password resets), and the credential used must carry the admin scope. Sessions

GET /api/me/sessions List your signed-in sessions

Browser logins and tokens made through POST /api/token of the current account. API keys are not sessions; they are listed under API Keys. Needs a browser session or an all-scope (*) credential; a stream key or a narrowly scoped key or token gets 403. Each row has an opaque public id (never the token), kind (browser or token), device, browser and os read locally from the User-Agent, created_at, last_used_at, expires_at (ISO-8601 UTC), ip (login), last_ip (last use, written at most once a minute) and current.

DELETE /api/me/sessions/{id} Sign out one session

Signs out the session with that public id. The session making the request cannot be signed out here (400, use logout); an unknown id or another member's session returns 404. Sockets, voice call and in-flight proxied downloads opened with it end at once (close code 4001); other sessions are not affected. Same credential rules as the list.

POST /api/me/sessions/revoke-others Sign out other devices

Signs out every session of the account except the one making the request. API keys and stream keys are not revoked. Returns {"status": "ok", "revoked": n, "websockets_closed": n}. Same credential rules as the list.

GET /api/push/config Web push: is it on, and the public VAPID key (1.19.0)

Needs a browser session or a bearer token with the full scope; API keys, stream keys, a token in the URL and narrow tokens get 403. Answers {"enabled": true, "public_key": "...", "max_devices": 10, "worker_url": "/sw.js", "worker_scope": "/push-sw/"}. A push is sent for a direct message, an @mention or @everyone and a followed stream going live, only to a member with a device and no open chat socket, with no message text and no sender name.

GET /api/push/subscriptions List your push devices (POST registers one)

GET returns {"devices": [{"id", "label", "service", "created_at", "last_success_at", "failure_count", "this_session"}]}, never an endpoint or a key. POST takes a PushSubscription as JSON ({"endpoint", "keys": {"p256dh", "auth"}}): 201 created, 200 updated, 400 for an endpoint that is not https on port 443 to an allowed push service (fcm.googleapis.com, updates.push.services.mozilla.com, *.push.apple.com, *.notify.windows.com and hosts a superadmin adds), a name that resolves to a private, loopback, link-local or metadata address, or bad keys; 403 while push is switched off; 409 at 10 devices or when another account holds the endpoint; 429 after 10 lookups a minute. With "rebind": true in the body it only ties a device this member already holds (same endpoint and keys) to the calling session and answers 200, or 404 when the member does not hold it; it never registers or moves a device, needs no name lookup and is not counted against the subscribe limit. When the endpoint and both keys belong to a different member (this browser, signed in as someone else now), that member's device is deleted and the answer is still 404. A device records when a signed-in session last announced it (a subscribe or a rebind); when its registering session has expired, is gone or was never recorded and nothing announced it for 30 days, nothing is sent to it and the periodic cleanup deletes it. A device whose session is live is not affected.

DELETE /api/push/subscriptions/{id} Remove one of your push devices

404 for a device that is not yours. POST /api/push/unsubscribe with {"endpoint": "..."} removes your device with that endpoint and always answers {"status": "ok"}; DELETE /api/push/subscriptions removes all of your devices. A device is also removed when the session that registered it ends, and when the account is deleted.

GET /api/admin/push Push settings and test push (superadmin)

GET returns {"enabled", "default_hosts", "allowed_hosts", "subject", "effective_subject", "device_count", "key_state", "key_problem"} (key_state: ok, none, unreadable or plain; key_problem says why push stays off when the stored key cannot be decrypted). PUT takes any of enabled, allowed_hosts (host names or *.suffix; no IP addresses, localhost or internal names) and subject (an https address or null). Changing allowed_hosts needs a superadmin's browser login session (a bearer token gets 403) and is audited with the new list. POST /api/admin/push/reset-key with {"confirm": true} replaces the VAPID key pair and deletes every device of every member; it needs a superadmin's browser login session (a token or key gets 403) and is audited as push_key_reset. POST /api/admin/push/test sends a test push to your own devices and returns one result per device. The same credential rule as the device routes applies, and the account must be a superadmin.

GET /api/push/prefs Which kinds of push you want (PUT changes them)

GET returns {"prefs": {"dm": true, "mention": true, "golive": true}, "kinds": [...]}, your own switches (all on until switched off). PUT takes one or more of those keys with true or false and returns the full set; an unknown key, a non-boolean value or an empty body is 400. Same credential rule as the device routes.

POST /logout Sign out and remove this browser's push device

Like GET /logout but answers 200 {"success": true} instead of a redirect. With {"endpoint": "..."} in the JSON body (never in the URL) it also removes your push device with that endpoint, even one an earlier session registered; another member's endpoint removes nothing.

GET /sw.js Push service worker (and /manifest.webmanifest)

No session needed; identical for everyone. push and notificationclick handlers only, no fetch handler, Cache-Control: no-cache, Service-Worker-Allowed: /push-sw/. /manifest.webmanifest is the web app manifest with generated icons.

POST /api/users/{id}/sessions/revoke Admin: sign a user out everywhere

Revokes every browser session and token of the user and closes what was opened with them. Needs the admin role (read from the database, so someone just promoted can use the session they already hold) and a full-scope credential (a browser session, or a token or key made with *; a stream key or scoped key gets 403), and follows the same role hierarchy as password resets (403 otherwise). API keys and stream keys are not revoked. On your own account the session you are using is kept. Written to the audit log as sessions_revoke.

User Connections

User Connections are personal remote access points that you configure for your own use. Unlike Services (admin-configured), connections are private to each user.

Connection IDs: Connection IDs are opaque URL-safe tokens (e.g., aB3x_kLm9pQ2rStU), not sequential integers. Use the id field returned by the API for all operations.
Security: User connections cannot target localhost or local network addresses (127.x.x.x, ::1, etc.) for security reasons.

Stored SSH password

For ssh and sftp connections, config.credential_mode is "prompt" (default: the terminal asks every time) or "stored" (the terminal opens without asking and the SFTP browser uses the same password, also for users the connection is shared with). config.password is write-only: responses carry only has_stored_password, never the value, for the owner and for a user the connection is shared with. Only the owner's POST and PUT can set it. An absent password keeps the stored one, a new one replaces it, an empty one or credential_mode: "prompt" clears it. A password without credential_mode never switches a connection to "stored": on a row whose mode is "prompt" it is a 400; on create, or on a row that has no mode, it is kept and the row stays without a mode (the terminal still asks, the file browser uses the password); on a "stored" row it replaces the password. Changing host, port, config.username or type clears it (a row moved to a type other than ssh or sftp keeps no stored password and no mode) unless the same request carries a new one; the response then has "stored_password_cleared": true. 400 for an unknown mode, a password that is not a string (at most 1024 characters), "stored" without a password, "stored" together with host_key_ignore: true, or a password with key authentication. The password is only sent to a host whose key is pinned and verified. Revoking or expiring a share closes the grantee's open terminal and SFTP connections (close code 4010).

Who May Watch

The HLS, WebRTC playback (WHEP) and info addresses above, and the thumbnail, follow one rule since 1.16.0. The stream's owner and administrators always may watch; any other signed-in member only a public stream; somebody not signed in only a stream that is public and has the open share link on (allow_unauthenticated), using its current pub_ key. The credential is the session cookie, or a token or API key with the all-scope *; a stream key (live_) and scoped API keys never authorise watching. Everything else answers 404 with {"error": "Stream not found"}, never 401 or 403, so a private stream's existence is not revealed. Access-Control-Allow-Origin: * is sent only for a public stream with the open link on. A change of visibility, open link or key reaches viewers within 5 seconds (normally at once). Relays, the recorder and the thumbnail capture read MediaMTX directly on loopback and are not affected.

Viewer heartbeat (1.17.0). POST /api/stream/{key}/viewer is what the watch page sends every 10 seconds while the video plays, so viewer_count is right. It follows the same access rule and credentials as playback: a request that may not watch, an unknown key and a stream key all answer the same 404 and count nobody. A signed-in viewer counts once per account; a viewer who is not signed in is identified by the optional X-Viewer-Id header (16 to 64 characters of A-Z a-z 0-9 - _) or by a salted hash of address and browser string (the portal's watch page sends the header but requires a sign-in, so a logged-out viewer is normally a player that sends none), with at most 5 anonymous viewers per address and 5000 per stream. HLS playlist fetches, WHEP offers and the PATCH of a WHEP session count the same way (an external WHEP player must call this route about every 10 seconds to stay counted); segments and thumbnails do not. Answers: 200 {"ok": true}, or 429 with Retry-After above 300 per minute per address (about 40 viewers beating every 10 seconds behind one address), or after 60 refused heartbeats (404) from one address in a minute; a refused heartbeat is charged only to the 60 refused allowance. A viewer leaves the count 15 seconds after the last heartbeat (20 after the last playlist). No address or list of viewers is stored or returned. The owner's stream detail carries last_peak_viewers and last_unique_viewers for the last finished live session (null until one is recorded); other members do not get them.

The Portal watch page /watch/{id} has a picture-in-picture button next to Fullscreen (also on /live). Publishing via WHIP (same network only)

Not available through the public proxy. The offer and answer travel through Portal on port 443, but the media does not. It flows directly between the client and MediaMTX's WebRTC media port (UDP/TCP 8189 by default), which the configuration Portal generates binds to loopback and which never passes through the public proxy. WHIP and WHEP therefore work only where the client can reach that port directly, for example on the same network after changing the WebRTC bind addresses in the MediaMTX configuration. From the internet, publish with RTMPS and play back with HLS.

const ws = new WebSocket('wss://portal.example.com/ws/ssh/1?token=...');

  // Send terminal size
  ws.send(JSON.stringify({

  const msg = JSON.parse(event.data);

Chat/Forum

Real-time multi-user chat with channels. Messages are encrypted at rest and automatically deleted after 7 days.

Security: All messages are encrypted using AES-256 (Fernet) before storage. Messages older than 7 days are automatically purged.

Display Name Priority

Chat display names follow this priority order:

  1. Anonymous — If anonymous mode is enabled, displayed as "Anonymous" with no avatar or nickname
  2. Nickname — If set via PUT /api/me/nickname
  3. Username — The account username (fallback)

Anonymous state is stored per-message, so messages sent while anonymous remain anonymous even after the user turns anonymous mode off.

Message Rate Limiting

Chat messages are rate limited to 5 messages per 5 seconds per user. If exceeded, the server responds with an error and the message is not sent.

PUT /api/chat/channels/{id}/retention Set a channel's retention ADMIN

Administrators only (1.20.0): a moderator or channel moderator gets 403, and the generic channel update ignores these fields. The chat socket has no channel-settings path for retention.

Request

{"retention_days": 30, "file_retention_days": 7, "confirm": true}

retention_days: days after which the periodic cleanup removes the channel's messages (pinned ones stay). A number, 0 or "forever" (stored as the cap, setting retention_chat_max_days, default 3650), or null to follow the global setting. A channel with its own value is no longer touched by the global chat retention. The cap limits a value when it is set; lowering retention_chat_max_days afterwards does not shorten a value already stored. A value of 0 or less found in the database (only a manual edit can store one) is read as no value, never as one day. file_retention_days: removes only the uploaded files of older messages (the message stays, marked file_removed) and can never exceed the message retention (400). A field left out is kept.

A change that makes removal sooner is applied only with "confirm": true. Without it nothing changes and the answer is {"applied": false, "confirm_required": true, "would_remove_messages": 12, "would_remove_files": 3}; "dry_run": true only looks. Applied: {"applied": true, "retention_days": 30, "file_retention_days": 7, "capped": false, "next_cleanup_at": "..."}. Audited as channel_retention_change with the old and new value. Errors: 400 (bad value, including a non-finite one such as Infinity or NaN or a number above 1000000000, file value above the message value, a stream's own chat), 403, 404.

The channel list and the channel_info frame carry retention_days, file_retention_days and retention_next_cleanup for a channel with its own value.

POST /api/chat/channels/{id}/prune Prune messages in a date range MOD

Administrators and the moderators of that chat per chat_mod_level (global staff, a stream's owner, a stream mod). A channel the caller may not read, and a caller with no moderator level in it, get 404 {"error": "Channel not found"}. The prune removes only what the caller could delete one message at a time: a stream mod the posts of ordinary members, the stream's owner everybody's but staff (the go-live card is the owner's), a global moderator or administrator everybody's of a lower role, everybody their own. A user filter on someone the caller may not act on counts 0, and a range prune leaves those posts.

Request

{"from": "2026-11-21T10:00:00Z", "to": "2026-11-21T11:00:00Z", "user": "alice", "skip_pinned": true, "dry_run": true}

from and to (ISO 8601, both required, both inclusive, no offset = UTC; a to later than the moment of the request ends at that moment, so a message posted while the prune runs is never taken). user (optional): an account id or a username; a user filter never matches an anonymous message, for anybody (an administrator included), so the history never shows whose the others were. Without a user filter, an anonymous message in the range is matched for every caller but an administrator whoever wrote it (the rank rules cover named messages only), so a count cannot tell the rank of its author. An administrator's prune without a user filter leaves anonymous messages alone when the rank rules exclude any author (another administrator or a superadmin), so nothing shows which of them survived. skip_pinned (default true). A dry run answers {"count": 12, "margin": 2} and removes nothing. A real run must send that count as expected_count; it is 409 (with the live count) when the live count differs by more than the margin, which is max(2, 2 percent) of the count the dry run showed (the count and margin of the dry run, and the expected_count you send back; the 409 repeats it as margin). 400 without it and for a value that is not a whole number up to 1000000000, a user id beyond the account id range, or a non-finite number (Infinity, NaN). Success: 202 {"started": true, "count": 12}.

The prune runs as a background task in batches of 200 that yield to the event loop. The room receives one messages_pruned frame per batch ({"type": "messages_pruned", "channel": "general", "ids": [41, 42]}, ids only), and one audit entry chat_prune is written when it ends. Upload files go with their messages. One prune per channel at a time (409). GET on the same path returns {"running", "status", "removed", "total", "files"} of the last prune, same gate.

Voice Moderation and the Room Cap

voice_state (join and resume) also carries locked, can_moderate (staff, and in a stream's own chat its owner and stream mods; never in a DM call) and room_cap; each user entry has server_muted. A voice_join is refused with voice_denied carrying a code and a message, sent to the joiner only and nothing to the room: timed_out (timed out or muted in that channel; moderators are exempt), room_full (the room holds voice_room_cap people, default 8, 2 to 25, DM calls included; a resume of a member already in the room is never refused for it), locked (the room is locked and the member has no moderation power), kicked (removed by a moderator less than 60 seconds ago). The moderation frames need a moderation level in that chat (error "Moderator access required"), never act on oneself or on a member of equal or higher level (error "Not allowed") and are refused in a DM call; each change is audited as voice_kick, voice_server_mute, voice_server_unmute, voice_lock or voice_unlock. A timeout or mute in a channel also removes the member from that channel's voice room. Every voice_signal is dropped unless the sender is in that room and so is the target. Server mute is cooperative, and a kick is enforced against normal clients only: the server cannot cut an existing peer-to-peer link of a modified client. The cap is set with PUT /api/admin/voice (superadmin).

Voice Reconnect

When the socket that owns a voice session closes, the session is kept for 20 seconds. Other members receive voice_user_reconnecting instead of voice_user_left, then voice_user_resumed if the same account resumes in time, or voice_user_left after about 20 seconds. Members that are reconnecting show reconnecting: true in voice_state and voice_reconnecting: true in the users list, receive no voice messages and are skipped when broadcasting. A password reset, role change, account delete, logout, a revoked session or anonymous mode ends a session at once, also while it is being held; making the channel private removes the members who may not stay. Closing a second tab does not affect the call. Audio between browsers does not go through the socket, so a short drop often does not interrupt it; the client re-negotiates only the peers that are no longer connected (an offer with fresh: true). iOS suspends background pages, which still ends a call.

Per-User Volume and Local Mute

Each member can set a playback volume (0 to 200%) and a local mute for every other member of the call they are in. Right-click or long-press a name in the voice bar or the online-users list (or focus it and press Enter, the context-menu key or Shift+F10) to open the popover. Both settings change only what that browser plays. They are stored in that browser's localStorage as voice_peer_prefs_<own user id>, keyed by the other member's user id, and are never sent to the server: there is no endpoint and no WebSocket message for them, and other members cannot see them. Deafen silences everyone whatever the per-user settings are. On iPhone and iPad, and where Web Audio is unavailable, audio plays through the audio element and the slider stops at 100%; iOS Safari may ignore element volume, so there only the local mute is certain to work, and the popover says so when the device refuses a volume. A member who is anonymous in a channel cannot be in a channel call, and the online-users list gives other members no user_id for them, so no setting can be attached to them there; in a direct-message call they appear as "Anonymous" with the account id the call payload already carries.

Voice Modes

Users can choose between two voice activation modes (stored in browser localStorage):

  • VAD (Voice Activity Detection) — Detects speech using AudioContext analysis with a configurable dBFS threshold. The track sent to the other members is disabled while the member is silent and enabled when the level passes the threshold, staying open for 750 ms after the last loud moment. A disabled track carries silence; some browsers still send keep-alive packets.
  • PTT (Push-to-Talk) — Transmit only while holding a configurable key (default: Space), plus an optional release delay of 0 to 1000 ms that keeps the microphone open after the key is released.

Voice Setup (Client Only)

The voice settings window in chat chooses the microphone and, where the browser can set the speaker of an audio context (Chromium browsers), the speaker; it shows a live level meter with the VAD threshold on it, and has an opt-in loopback test that plays the member's own microphone through their own speakers (not available during a call, never sent to anyone). The choices are stored in that browser's localStorage as voice_prefs (mode, pttKey, vadThreshold, pttDelay, inputDeviceId, outputDeviceId), plus the marker voice_gate_notice_seen (value 1) that records that the one-time notice about a strict saved threshold (above -35 dBFS) has been shown, and are never sent to the server: there is no endpoint and no WebSocket message for them, and voice_join, voice_speaking and voice_signal are unchanged. The chosen microphone is used on the next join; changing it during a call replaces the track in each connection with replaceTrack, without a new offer, a voice_leave or a new join, so the resume token stays valid. Outside a call the meter opens the microphone while the settings window is open and releases it when it is closed; during a call it reads the call's own microphone. With a push-to-talk release delay, voice_speaking with speaking: false is sent when the delay ends.

Message Search

Full-text search across chat channel messages and DM conversations. Powered by SQLite FTS5 for fast, ranked results. Search respects access control — users can only find messages in channels they have access to and DM conversations they participate in.

Privacy Note: An FTS5 plaintext search index is maintained alongside the encrypted message storage to enable search functionality. The search index contains message text in plaintext for indexing purposes. Search results are always filtered to the authenticated user's accessible messages.
GET /api/chat/search Search messages

Search across channel messages and DM conversations. Rate limited to 10 requests per minute per user (a request refused for a bad query or parameter does not count). The search fails closed: if the readable channels cannot be worked out, the answer is 503 {"error": "Search is unavailable right now"} and nothing is searched. Channel results cover only the channels the caller may read: a private channel needs membership (admins and superadmins search every channel), and the chat of a stream that is not public (is_public off) is searched only for the stream's owner and admins, the rule of the channel history. The text of q holds words and operators.

Query Parameters

ParameterTypeDescription
q string Words and operators (2-200 characters), see below required
scope string Search scope: all (default), channels, or dms
channel_id integer Limit search to a specific channel (1 to 9223372036854775807; any other value answers 400)
conversation_id integer Limit search to a specific DM conversation (same range as channel_id)
from, has, before, after string The older way to give those operators; they go through the same checks as in q
limit integer Results per page (default: 25, max: 50)
offset integer Pagination offset (default: 0, at most 2000; a larger value answers 400 with offset must not exceed 2000)

Operators in q

OperatorMeaning
from:name, -from:nameAuthor by account name or nickname (any case); - leaves that author out
in:channel, -in:channelChannel by name (a leading # is ignored); - leaves it out. DMs are not searched when in: is given
has:link, has:file, has:imageText with an http(s) address; an attachment that is not an image; an image or image attachment

before:YYYY-MM-DD, after:YYYY-MM-DDCreated before the start of that day, or from the start of that day (UTC)
"two words"A phrase

Anything else is a word that must appear. A query of only operators is allowed: newest first, at most 200 results in total (capped). 12:30 and https://example.com are searched as text; any other name:value is an unknown operator — put such text in double quotes. An unknown operator or value, a bad date, a negated operator other than from: and in: or more than 10 operators answer 400 with a message in error. An in: naming a channel you cannot read matches nothing, exactly like a channel that does not exist.

Word queries are ordered newest first when scope is all (the default), so offset pages through every match once; with scope=channels or scope=dms they are ordered by relevance.

A positive from: never matches an anonymous post for an ordinary member, and a negated -from: never removes one, so neither the filter nor a count shows who wrote it. Moderators and admins, who already receive the author id, can match it. Results are masked exactly like channel history.

Webhooks

Webhooks let you receive real-time HTTP notifications when events happen in your portal (outgoing), or post messages into chat channels from external services (incoming). Outgoing webhooks sign payloads with HMAC-SHA256 for verification. Stream keys are refused (403) on every webhook route. Creating, changing or deleting a webhook and getting a new signing secret need a browser session or an all-scope (*) token or API key; a narrowly scoped key can only list, read and view logs of its own webhooks (testing a webhook triggers a delivery and needs a full-scope credential too). Webhook URLs, secrets, and delivery log payloads are encrypted at rest. Admin+ required for management.

POST /api/webhooks Notification formats: ntfy, Gotify, Discord, Slack

Outgoing webhooks take a format: generic (default, unchanged, HMAC-signed), ntfy, gotify, discord or slack. The other formats are not signed and need no secret. A hook in another format stores no signing secret; changing it to generic creates one (read it with regenerate-secret) and changing it away from generic removes it. They send an event title, a one-line summary and the portal name only; include_details (default false) adds a short allow-listed set of fields of the event, for alert events also the address and user agent involved; never email addresses or tokens. Message text is cut to 200 characters and mentions are removed (Discord payloads set allowed_mentions to none, and markdown link and formatting syntax in Discord text is escaped so [text](url) shows as typed). Redirects are not followed and HTTPS is required unless allow_private is on, at delivery as well as when the hook is saved.

ParameterTypeDescription
formatstringgeneric, ntfy, gotify, discord, slack
format_configobjectWrite-only credentials: Gotify {"token"} (required), ntfy {"token"} or {"username","password"}. Stored encrypted, never returned (responses show has_format_secret). An edit that omits it keeps the stored value, unless the same edit moves the hook to a new scheme, host or port (or switches allow_private off while changing the URL): then the stored credentials are dropped, and Gotify is refused with 400 until the token is sent again.
include_detailsbooleanAdd the detail fields of the event (default false)
allow_privatebooleanLet the hook reach loopback and LAN addresses, for a self-hosted ntfy or Gotify (default false). Only a superadmin with a browser login session can turn it on (a request that authenticates by API key or bearer token never can, whatever cookie it also carries); any editor can turn it off, and turning it off is never re-checked against the address. Plain http:// is accepted only when every resolved address is private or loopback. Link-local, cloud metadata, 0.0.0.0/8 and the portal's own ports stay blocked. A hook is re-checked against the default policy only when it is created, when its URL or format changes, or when allow_private is switched on; saving it with the same URL and format (rename, disable, other events, allow_private off) is never refused for the address.

For a non-generic hook the destination URL is never returned: responses carry url: null, url_set, url_host (scheme and host) and has_format_secret. Changing the format of such a hook to generic needs a new url in the same request (otherwise 400), because the URL of a generic hook is returned.

The stream.live payload (1.16.0): data has stream_id, stream_name, owner_username, streamer (nickname, else username), title, game (1.17.0, empty when none), url (the logged-in watch page, <base>/watch/<id>, built from PUBLIC_BASE_URL or HOSTNAME, never from a request header) and message (the owner's go-live message, filled in). public_key is no longer part of it, and no payload carries a stream key, a pub_ key, an RTMP address or a path. A stream is announced at most once per 10 minutes. For a stream that is not public, stream.live and stream.offline go only to system hooks in the generic format, never to a member's own hook or a non-generic hook. In the non-generic formats the streamer, title, message and watch URL appear only with include_details on.

message.created, user.connected and user.disconnected reach a non-generic hook only when listed by name (* does not include them); the two presence events are never sent for a member whose status preference is appear-offline. A user hook can subscribe only to the documented events (any other event is system-only). The generic format receives full event payloads, including the text of messages in private channels, so point it only at a receiver you control. Two rules hold for every format, generic included: the presence events are sent to no hook for a member who appears offline, and an anonymous post's message.created carries user_id: null (message.deleted carries deleted_by: null when the author deleted it). message.created goes only for channels an ordinary member can read (never private channels or the chat of a stream that is not public; anonymous posts show as "Anonymous"). stream.live and stream.offline are sent only for public streams.

A 429 answer waits for Retry-After (capped at 10 minutes, at most 3 waits in all for one delivery, retries after a failure included; the hook is checked again after each wait and nothing more is sent if it was switched off, deleted, changed or unsubscribed meanwhile) and never counts toward the automatic disable after 10 failures. A delivery refused by policy before anything is sent (a non-generic hook over plain http:// with allow_private off) sets the hook's last failure reason to a fixed text without the URL and counts toward those 10 at most once per hour.

Alert events

Fifteen ops, security and moderation events in three groups (Security, Operations, Moderation) go to system webhooks that list them by name: * never includes an alert, a user hook cannot subscribe to one, and nothing is subscribed by default. Security: auth.login_failed_burst, 2fa.disabled, apikey.created, role.changed, ip.blocked. Operations: update.available, service.health_changed, cert.expiring, cert.renewal_failed, gameserver.crashed, backup.ok, backup.failed, alerts.suppressed. Moderation: moderation.action, automod.triggered.

Generic body: data holds title, summary, severity, group, and details only for a hook with include_details (addresses, user agents, reasons, rule names). A member who posts anonymously is never named. All alerts together are capped at 30 per 10 minutes, and an alerts.suppressed notice is due whenever an alert is held back (it counts in the window); an alert event dropped for a system webhook that is waiting out a 429 from its receiver is counted too, with the reason "receiver asked to slow down". What a stranger or an ordinary member can set off has a smaller cap of its own in the same window: 5 auth.login_failed_burst and 5 automatic-block ip.blocked alerts per 10 minutes, 5 in all for the moderation alerts any signed-in member can set off (moderation.action and automod.triggered share that one cap), 3 2fa.disabled and 2 apikey.created (a cap each), so they cannot use up the room of the other alerts or of each other. They bind only alerts caused by non-staff accounts: an alert whose actor is a moderator, admin or superadmin, one about a staff account, and every operations alert bypass them (own cooldown and the global cap only), and the global cap keeps a reserve of 10 of the 30 for them. The one exception is the failed-sign-in burst against a staff account name (a stranger can set it off): it may use at most 5 of the 10 reserved slots in a 10-minute window (it is held back once 25 of the 30 slots are used). The first alerts.suppressed notice is sent 30 seconds after the first alert is held back, then at most one per 10 minutes; each names every kind held back since the previous notice with its count (the commonest first; kinds that do not fit are counted as "and N more kinds") and the limit that held it back (global limit, reserve or per-kind limit), then clears those counts. It is never held back by a cap and goes to every system hook with any alert event subscribed. Wrong second-factor codes count toward auth.login_failed_burst, and a burst held back is still written once to the security event log. A moderation or automod alert from a private channel, a conversation or a non-public stream chat says "in a private channel" in the ntfy, Gotify, Discord and Slack formats, with no channel or stream name even in the details. A backup whose extra copy failed sends backup.failed, not backup.ok. role.changed rests 60 seconds per account and role change.

Path Parameters

ParameterTypeDescription
connection_idstringConnection ID (opaque token) required
pathstringPath to proxy to the backend service

Behavior

  • Forwards all HTTP methods (GET, POST, PUT, DELETE, etc.) to the backend
  • Proxies WebSocket upgrade requests for real-time features
  • Enforces TLS for connections to HTTPS backends
  • In browser mode, the path encodes the full target URL (e.g., /proxy/{id}/https://example.com/page) for multi-site navigation
  • Localhost and private IPs are blocked for browser-mode targets
  • Portal session cookies and Authorization headers are stripped from upstream requests
  • The upstream always receives X-Forwarded-For and X-Real-IP (the client's address, resolved the same way as for rate limiting), X-Forwarded-Proto (the scheme the client used, believed from CF-Visitor / X-Forwarded-Proto only when they come from a trusted proxy), and, only when the connection has forwarded_host on (default off), X-Forwarded-Host (the portal's configured host name, never a name the client chose) and X-Forwarded-Prefix (/proxy/{id}). A ?token= query parameter that authenticated the request is removed before it is forwarded. Copies of these headers sent by the client are never passed on, nor are CF-Connecting-IP, True-Client-IP, X-Client-IP, Authorization, the portal session cookie, X-API-Key or X-Stream-Key, even when forward_headers matches them. In browser mode only X-Forwarded-Proto is sent, so the sites a member visits learn nothing about the member or the portal.
  • Upstream redirects are followed by the portal itself (at most 5 hops, every hop dialled through the outbound host policy); a Set-Cookie from an intermediate hop is not passed on, and no further hop is made once the member's session was revoked. In browser_mode the 3xx goes to the browser instead, with its Location kept under that site's own path (a protocol-relative //host/path names that host, with the current site's scheme). A Location that still reaches the browser from a single-site connection is kept under /proxy/{id}/, except one on the upstream's host with another scheme or port, which is returned unchanged
  • Every upstream Set-Cookie is kept: each Path is moved under the proxy path, a missing Path becomes the proxy root, and Domain is removed so the browser stores the cookie. In browser_mode the path is that of the site, so one site's cookies are never sent to another. An upstream cookie named like the portal's own session cookie is dropped
  • The connection's timeout (5-300 s, default 60) is the longest the upstream may stay silent; connecting is limited to 10 s. A download passed through as it arrives has no total time limit; a response rewritten in memory (HTML, CSS, JavaScript, JSON) must arrive within this time in total. A silent upstream gives 504. Revoking the member's sessions (also signing out, or revoking one session or an API key) ends the in-progress downloads opened with them
  • Requires authentication — only the connection owner can access their proxy routes

Session Recordings ADMIN

Recorded terminal and SSH sessions (asciicast v2). Only administrators (role admin or superadmin) can use these routes, with a browser session or an all-scope (*) bearer token. Anyone else who is signed in gets 404 for every route and every id, a request without a credential gets 401, and every API key (also one made with *) and every narrowly scoped token gets 403: no existing scope covers recordings. A file name or path is never returned. Recording is off per connection unless its config has "recording" set to true, 1, "1" or "true" (any case), and only an administrator can set or clear that flag (a member's value is ignored without an error); it is also limited by the recordings disk budget (setting recording_max_total_mb, free-space floor). Input is never recorded.

Returns {"recordings": [{"id", "user", "user_id", "connection", "type", "started_at", "ended_at", "duration", "size", "live", "interrupted"}], "total", "page", "limit"}. A running session has live: true and no end time. interrupted: true marks a session that a restart of the portal cut short: at the next start its row gets the size of its file, the time of the file's last complete event as duration (and so an end time), and this flag; a recording whose file is missing is left as it was.

GET /api/recordings/{id}/cast Play or download a recording ADMIN

The recording file, Cache-Control: no-store; ?download=1 sends it as an attachment. The file is found through the database row only and must be a plain file inside the recordings folder (no symlink, no path in the name): any other row is 403, a missing file 404. Audited as recording_play or recording_download with the administrator, the recording id, its owner and its connection; if the entry cannot be written the answer is 500 and nothing is sent.

DELETE /api/recordings/{id} Delete a recording ADMIN

Removes the row and the file; 409 while the session still runs. Audited as recording_delete (written before anything is removed, details outcome: "requested": it records the request, not the result). If the file cannot be removed (including when the recordings folder fails its safety check, so a file that may still exist is never left without its row), or the row cannot be deleted afterwards, the answer is 500 and a second entry, recording_delete_failed, with the reason, is written; entries are never rewritten. Returns {"deleted": 7, "file_removed": true} (false only when the row's stored name was not a plain file name: the row is removed and no file was touched). The four audit actions (recording_play, recording_download, recording_delete, recording_delete_failed) are visible to administrators, not to moderators.

Security Events SUPERADMIN

A separate log of authentication and credential events. It has its own table because the audit log needs a signed-in actor and cannot hold a failed login for an unknown user; its rows are kept when an account is deleted. Reading and exporting need the superadmin role on a credential with admin scope; others get 403. Backup runs, downloads, deletes and settings changes stay in the audit log only.

Auth events: login_success, login_failed (result unknown_user or bad_password), 2fa_required, 2fa_passed, 2fa_failed, 2fa_throttled, backup_code_used, logout, session_revoked (result own, others or admin_all for the sessions page and the admin sign-out), register_failed. Security events: 2fa_enabled, 2fa_disabled, 2fa_disable_failed, api_key_created, api_key_revoked, api_key_deleted, password_changed, password_change_failed, password_reset, user_created, user_deleted, role_changed, invite_created, invite_deactivated, ip_blocked, ip_unblocked (admin or command line), probe_block (automatic), never_ban_changed, login_ban_changed, cf_ranges_refreshed (result ok or failed, run by the weekly job), cf_ranges_reset (use the built-in list), cf_ranges_approved and cf_ranges_dismissed (a pending list approved or dismissed, counts only), cf_refresh_toggled (the weekly refresh turned on or off, was and enabled), security_retention_changed (old_days, new_days of retention_security_events_days), security_events_pruned (a manual run of cleanup deleted events: deleted, days), rate_limited, host_key_accepted, security_log_export.

Aggregation: wrong passwords, bad or missing 2FA codes, failed registrations, wrong current-password attempts, probe blocks and rate-limit trips are counted per (source IP, event, result, minute) and written as one row with a count, every few seconds and at shutdown. An IPv6 source is counted as its /64 network (ip is then written 2001:db8:1:2::/64; a full IPv6 address typed in the ip filter also matches its /64 row, and a typed /64 matches it directly). At most 300 aggregated rows are created per minute across all sources, over every flush; further sources in that minute are added to one shared row per event and result with ip * and no username_tried, user_agent or details. Such a row keeps the first username_tried and user_agent of that minute. Everything else is written at once, at most 30 rows per minute for each account (or address, without an account) and event; the rest of that minute is counted in one aggregated row per account, which keeps the account and has ip *. These events are never held to that limit or folded into an overflow row: role_changed, user_deleted, password_reset, never_ban_changed, login_ban_changed, every cf_* event, security_retention_changed, security_events_pruned, security_log_export, and ip_blocked and ip_unblocked made by an administrator. Passwords, 2FA and backup codes, tokens, API keys and invite codes are never stored. username_tried is cut to 64 characters and user_agent to 200; control, zero-width and bidirectional override characters are removed.

Auto-Moderation ADMIN

Configure automatic message filtering rules that run before messages are saved, and again when a member edits a message. A blocked message or edit is not stored and only its author is told. Moderators and above are still blocked, but are exempt from the timeout and mute penalties. Triggers are logged to the audit log.

POST /api/admin/automod Create automod rule ADMIN

Create a new auto-moderation rule. The config is validated on creation and on update; an invalid config returns 400.

Regex rules

  • Each pattern is at most 500 characters, a rule has at most 100 patterns, and a pattern must compile.
  • A pattern that repeats a group which already contains an unbounded repeat, such as (a+)+$, is refused. This check is a heuristic and cannot catch every slow pattern.
  • Text is truncated to 2000 characters before a regex rule sees it, so text after that is not checked by regex rules. This bounds simple patterns only.
  • Patterns run in a separate worker process with a 0.25 second limit. A pattern that overruns it stops the worker and the message (or edit) being checked is rejected for its author with error code automod_unchecked (could not be checked; shorten or rephrase it); no penalty is booked, nobody else is told, and the pattern is tried again for the next message. Each rule in GET /api/admin/automod carries slow_pattern_timeouts, the number of such overruns of its patterns in the last hour.
  • Messages over the chat length limit (4000 characters, for new messages and edits) are rejected by chat and never reach automod.
  • Rules saved before these limits existed are checked again at run time; a pattern that fails is skipped and the rule list reports it in not_enforced_reason.

Rate Limits

API requests are rate limited to prevent abuse:

  • Authentication endpoints: 10 requests per minute
  • General API: 60 requests per minute
  • WebSocket connections: 10 concurrent per user
  • Chat messages: 5 messages per 5 seconds per user
  • Outgoing webhooks: 30 deliveries per webhook per 60 seconds
  • Incoming webhooks: 10 messages per token per 60 seconds

Rate limit headers are included in responses:

X-RateLimit-Limit: 60
X-RateLimit-Remaining: 58
X-RateLimit-Reset: 1704067200
